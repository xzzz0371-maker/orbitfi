## 1. High

### H1. 前端价格源指向主网未部署的 `SwitchableOracle`，且失败时静默使用硬编码价

- 位置：
  - `frontend/src/lib/hooks.ts:141`（`usePrices`）、`:269`（`useAssetPrices`）→ `ADDRESSES.switchableOracle`
  - `frontend/src/lib/config.ts:22`（`switchableOracle: deployments.switchableOracle`）
  - `frontend/src/lib/deployments/base.json:12` → `"switchableOracle": ""`
  - `frontend/src/lib/config.ts:41` → `FALLBACK_ETH_PRICE = 2506`
- 代码证据：
  ```ts
  // hooks.ts:141,269 均读 switchableOracle，而 base.json 里它是空串
  const { data: ethRaw } = useReadContract({ address: ADDRESSES.switchableOracle as Address, ... });
  const ethUsd = ethRaw !== undefined && ethRaw !== null ? Number(ethRaw) / 1e8 : FALLBACK_ETH_PRICE;
  ```
  而 `contracts/script/DeployMainnet.s.sol:19` 明确声明：**"不部署 SwitchableOracle"**（主网禁可设价通道）。
- 影响：
  1. 主网部署后，前端**永远读不到真实价**（地址为空 → 读调用必然失败）。
  2. `usePrices` 会静默回落到 **硬编码 $2506**，并被 `BorrowTab` / `StressTestPage` / `PositionPanel` 用于计算 LTV、Health Factor、可借上限。
  3. `useAssetPrices` 失败时返回 **0**，导致 `BorrowTab` 的 `collValueUsd = 0` → 按钮永久禁用并提示"No collateral"（功能死锁）；或在部分成功的组合下用 `market.address ?? 1`（**默认 $1**）估算可借额度。
  4. 用户看到的 HF/LTV 与链上真实值不一致 → **误判爆仓风险**。合约会拒绝越界交易，所以不会直接丢钱，但会误导用户在错误的时点加仓/减仓。
- 验证方式：`ADDRESSES.switchableOracle === ""`（已确认）；`DeployMainnet.s.sol` 不部署该合约（已确认）。
  - 修复建议：
    - `usePrices` / `useAssetPrices` 改用 `ADDRESSES.chainlinkOracle`（= `deployments.oracle`）。
    - **删除 `FALLBACK_ETH_PRICE` 与 `?? 1` 兜底**；读价失败时 UI 必须显示"价格不可用"并禁用借贷/清算相关操作（fail-closed），而不是猜一个价。
    - 加一个部署后断言：`deployments/base.json` 里所有非空地址必须 `code.length > 0`。
  - 详细修改步骤见 `docs/修改方案_2026-09-15.md` 批次 A1。

### H2. `maxStaleness = 3600` 与项目自己的 feed 心跳登记表（86400s）矛盾 → 平稳行情下全协议价格读取 revert

- 位置与证据：
  - `contracts/src/oracle/ChainlinkOracle.sol:36` → `uint256 public maxStaleness = 3600;`
  - `contracts/src/oracle/ChainlinkOracle.sol:163` → `require(block.timestamp - updatedAt <= maxStaleness, "stale price");`
  - `scripts/feed-health-check/feeds.ts:15-19` → **5 个 Base feed 的 `heartbeatSec` 全部登记为 `86400`（24 小时）**
  - `contracts/script/DeployMainnet.s.sol:273-276` → 部署预检**容忍 feed 陈旧到 26 小时**，且脚本**从未调用 `setMaxStaleness`** → 主网部署后运行时仍是默认 1 小时
- 三处数字互相矛盾（预检 26h / 登记表 24h / 运行时 1h），其中至少两个是错的。
- 触发路径（**不需要攻击者**）：
  1. Chainlink 是"偏差阈值**或**心跳，先到者触发"。USDC/USDT/DAI 这类稳定币偏差阈值极窄且几乎不动 → 平静时段只能靠心跳，间隔可达 24h。
  2. 某稳定币 feed 超过 1 小时未更新 → `getAssetPrice` revert。
  3. `_priceOf`（`LendingPool.sol:950-954`）被 `_debtValueWad` / `_collateralValueWad` 上游调用 → 该市场**借款、还款、抵押取回、清算全部 revert**。
  4. 叠加 M2 的 `_oracleAnomalous()` 全量遍历 → 任一资产 stale 即锁死**全池**新增敞口。
- 影响：按设计就会周期性发生的**可用性事故**，且窗口正好在低波动时段——此时清算通道也会一起失效，坏账会静默累积。**比 H1 更急**（H1 只误导前端读数，H2 直接让链上资金操作不可用）。
- 缓解（无需重部署）：`maxStaleness` 是 `PARAM_ADMIN` 可改的存储变量 → 立即设成与最长 heartbeat 相称的值（如 26h），并把默认 30% 的 `maxDeviation` 收紧到 10~15%。
- 根治：改为**逐 feed** 陈旧阈值（ETH 2h / 稳定币 26h），见修改方案 C13。
- 详细修改步骤见 `docs/修改方案_2026-09-15.md` 批次 B6 与 C13。

## 2. Medium

### M1. `RiskManager.setCloseFactor(0)` 可永久砖化清算

- 位置：`contracts/src/RiskManager.sol:72-76`
  ```solidity
  function setCloseFactor(uint256 value) external onlyOwner {
      require(value <= WAD, "factor>100%");
      closeFactor = value;
  }
  ```
- 影响：`closeFactor = 0` 时，`LendingPool._liquidateAmounts:689-693` 计算
  `coverWad = min(coverWad, debtWad * 0 / WAD) = 0` → `require(coverWad > 0, "cover=0")` **恒 revert**。
  即任何参数误设都会让**全协议清算能力归零**，坏账开始累积，且只能靠再次调参恢复（若走 Timelock 还有延迟）。
- 修复建议：加下限 `require(value >= 1e16 && value <= WAD, "closeFactor out of bounds")`（≥1%）。

### M2. 单一 feed 缺失/停更 → 全协议借款与抵押存入被 DoS

- 位置：`LendingPool._oracleAnomalous()`（`:940-948`）遍历**所有**市场 + **所有**抵押品调用 `isPriceAnomalous`
  → `ChainlinkOracle.isPriceAnomalous`（`:148-152`）→ `_readPrice`（`:159`）→ `require(address(f.aggregator) != address(0), "no feed")` / `"stale price"` **revert**
- 影响：
  1. `_supplyCollateralCore` / `_borrowCore` 都会先调用 `_oracleAnomalous()`。**只要任一资产（哪怕没人用的）feed 缺失或 stale，全池所有市场的抵押存入与借款全部 revert。**
  2. 典型触发场景：管理员用 `addMarket`/`addCollateral` 注册了新资产但**漏配 feed**，或某资产的 Chainlink 心跳短暂超时 → 跨市场可用性耦合。
  3. 属于可用性问题（fail-closed，不丢资金），但会锁住新敞口并阻碍用户降险路径之外的操作。
- 修复建议：
  - `_oracleAnomalous` 只检查**本次操作真正用到的**资产（供应/借款市场 + 用户持有的抵押品），而不是全量遍历。
  - 给 `ChainlinkOracle` 加"feed 已配置"的显式状态位，`LendingPool.addMarket/addCollateral` 时校验 oracle 已有该资产 feed（部署期一次性拦截）。
  - 补一个部署后自检：遍历所有注册资产调用 `getAssetPrice`，任一 revert 则视为部署失败。

### M3. `ChainlinkOracle` 的偏差保护依赖"有人主动调用 `updatePrice()`"

- 位置：`contracts/src/oracle/ChainlinkOracle.sol:31-34, 127-143, 165-169`
  ```solidity
  uint256 base = lastValidPrice[asset];   // 只有 updatePrice() 且非异常时才写入
  if (base > 0) { ... anomalous = true; }
  ```
- 影响：
  1. 部署后如无人调用 `updatePrice`，`lastValidPrice == 0` → **`maxDeviation` 永不触发**，偏差保护形同虚设。
  2. 该函数是 permissionless 的，但**没有任何 keeper/自动化保证它被周期调用**（`services/monitor` 只读 `getAssetPrice`，不调用 `updatePrice`）。
  3. `getAssetPrice` 在偏差时**不 revert**（设计如此，注释已说明"让清算可以继续"），因此偏差价格的"拦截"完全依赖 `isPriceAnomalous` → 又回到上面的 `lastValidPrice` 依赖。
- 修复建议：在 `services/monitor`（或独立 keeper）中把 `updatePrice` 纳入周期性写调用；或让 `_readPrice` 在 `lastValidPrice == 0` 时以首个采样价初始化基准；部署脚本中加一次初始化 `updatePrice` 调用。

### M4. `ReserveManager` 中的"物理储备"除坏账外永久无法取出

- 位置：`contracts/src/ReserveManager.sol:35-59`（全合约只有 `coverBadDebt` 一个出金口，且 `require(msg.sender == lendingPool)`）
  - 对比 `LendingPool._overflowReserveToTreasury:825-838`：只把**账面** `m.totalReserve` 转入 treasury，`transferable = min(overflow, m.totalReserve)`；一旦储备已被 `skimReserve` 划走（`m.totalReserve == 0`），`transferable` 恒为 0。
- 影响：已被 skim 到 `ReserveManager` 的储备金**只能用于覆盖坏账，永远不会流向 treasury**。
  文档宣称的"储备溢出→Treasury"仅对未 skim 的部分生效。属于资金效率/经济模型的实现缺口（不上审计报告的清单）。
- 修复建议：为 `ReserveManager` 增加 `onlyOwner` 的 `transferToTreasury(token, amount)`（目标地址白名单/固定 treasury），并在 `_overflowReserveToTreasury` 中一并处理物理储备的溢出部分。

### M5. 市场/抵押品注册后**无法停用**

- 位置：`LendingPool.Market.enabled` / `Collateral.enabled` 字段（`:48, 62`）**只在构造时置 1，全仓库无任何 setter 将其置 0**；
  `_market()`（`:968-971`）也不校验 `enabled`。
- 影响：若某资产（如 USDT）脱锚或 feed 长期异常，治理**没有"冻结该市场/该抵押品"的手段**，只能整池 pause（同时禁掉健康市场的新增敞口）。这是一个明确的运维/治理缺口。
- 注意：直接置 `enabled = 0` 会让 `_accrueMarket` 提前 return（`:791`）→ **该市场的债务停止计息**，属于错误实现。正确做法是新增 `marketFrozen` 语义：禁止新增 borrow/supplyCollateral，但**强制继续 accrual 且允许 repay/liquidate**。
- 修复建议：设计并实现 `freezeMarket(marketId)` / `freezeCollateral(collId)`（PARAM_ADMIN），语义"禁新增，保留计息与退出路径"，并补测试。

### M6. 主网部署脚本存在"静默回落"与校验缺口

- 位置：`contracts/script/DeployMainnet.s.sol`
  1. `:78-107` 所有 token/feed 地址都用 `vm.envOr("MAINNET_*", 0x内置地址)` —— **环境变量名拼错或漏填时不会报错，而是静默使用内置地址**。
  2. `_preflight`（`:256-278`）只校验 `decimals == 8`、`answer > 0`、26h 新鲜度，**不校验 `description()`**，无法发现"feed 地址张冠李戴"（喂的是 BTC 却当成 ETH）。
  3. `:129` `irm.setMarketGovernor(admin)` —— **admin 多签可绕过 Timelock 直接切换利率预设**（`InterestRateModel.applyPreset:87-98` 允许 owner 或 marketGovernor），与文档宣称的"参数变更需经 Timelock 延时"不一致。
  4. 只做 `_verifyEthTiers`（`:310-318`），**没有校验追加注册的 cbBTC/USDT/DAI 档位非零**。若 `_setRiskTiers` 漏配，该抵押品 `maxLTV = 0`（可存不可借，静默功能缺失）。
- 修复建议：
  - 必填项改用 `vm.envAddress`（缺失即 revert），仅对"确有官方默认值"的项保留 `envOr` 并在日志中显式打印"使用内置默认值"。
  - `_preflight` 增加 `description()` 断言（可直接复用 `scripts/feed-health-check` 的 `FEEDS` 表）。
  - 若启用 Timelock，则不设 `marketGovernor`（或设为 Timelock），避免绕过。
  - 增加对所有已注册资产的档位非零校验。

### M7. `MainnetDeployAndTransfer.s.sol` 缺少 self-check

- 位置：`contracts/script/MainnetDeployAndTransfer.s.sol:58-65`
  - **没有** `require(safe != deployer)`（`DeployMainnet.s.sol:59` 有）。若 `MAINNET_ADMIN_SAFE` 误填为部署者 EOA，则所有角色回到部署者手里，`renounceRole` 会把自己撤干净 → **协议失去所有管理能力（无人能调参/暂停）**。
  - `_envAddrOr`（`:42-48`）用 `try/catch` 吞掉 `vm.envAddress` 异常 —— 变量存在但格式错误时**静默返回默认值**。
  - `:64` `MAINNET_TIMELOCK` 传入后直接用，不校验该地址上是否已授予 `safe` 的 `PROPOSER_ROLE`/`EXECUTOR_ROLE`、`ADMIN_ROLE`。
- 修复建议：加 `require(safe != deployer && safe != address(0))`；移除 `try/catch` 静默回落；对 Timelock 做 `hasRole` 断言（脚本末尾已打日志但未 revert）。

### M8. `services/monitor` 覆盖面不足 + 告警只发一次

- 位置：`services/monitor/src/index.ts:99` (`for (const user of cfg.users)`)、`services/monitor/src/alerts.ts:17-24`
- 影响：
  1. 监控**只覆盖 `config/positions.json` 里硬编码的用户名单**。新开仓的用户不在名单内 → 可清算仓位**永远不会告警**。这直接破坏"及时清算→控制坏账"的核心风控闭环。
  2. `AlertStore` 是**边沿触发**（只在 `false→true` 翻转时推送），且**没有重复提醒/升级机制**。一条 CRITICAL 发出去后，若运维当时没看到，仓位会一直可清算而不再有提示。
  3. 协议已移除事件（EIP-170），所以没有 Subgraph/索引 → **无法发现新仓位**，这是架构性缺口（内部文档 §3.1-6 已提及，但监控实现没有兜底）。
- 修复建议：至少补一个"全量仓位发现"途径——重引入最小事件集（`Supplied/Borrowed/Repaid/Liquidated`）建 Subgraph，或由 `metrics.jsonl` 离线构建地址集合；`AlertStore` 增加 `reNotifyIntervalSeconds`（如每 15 分钟重复推送仍未恢复的 CRITICAL）。

## 4. 本轮复核确认"正确"的核心逻辑（供评审参考）

以下为逐行推导 + 与内部审计交叉验证后，**认为实现正确**的关键点：

1. **份额数学无 ERC4626 通胀攻击**：`supplyIndex` 只由计息（需 `totalShares > 0`）与坏账驱动，不随直接转账增长；`_supplyCore` 有 `require(shares > 0)`；池子**没有 `receive()`/`fallback()`**，ETH 无法被"捐赠"入账。`cash + borrows == totalSupply + totalReserve + treasuryAccrued` 的记账等式在各路径成立。
2. **坏账吸收守恒**（`_handleBadDebtCore`）：物理储备 → 账面 `totalReserve` → `supplyIndex` 稀释 → `treasuryAccrued`，逐项推导后资产端与负债端变动相等，未发现重复扣减或漏扣。D1 修复后的顺序与文档语义一致。
3. **清算数学**：`closeFactor` 封顶、`seizeValue ≤ 总抵押估值`、`seizeAmount ≤ userCollateral[collId]`、`minSeizeAmount` 滑点保护、`require(HF < 1)` 前置、自清算禁止 —— 边界齐全；超额抵押品不足时 `seizeAmount` 被钳制而 `coverAmount` 不缩水，方向**有利于协议而非清算人**。
4. **全局 tier 不变式**：`userGlobalTier != 0 ⇔ 存在任一市场有债`；`_anyBorrow()` 在 repay/liquidate/handleBadDebt 后一致维护；`_borrowCore` 在计算 HF **之前**写入 `userGlobalTier`，无首借窗口漏洞。
5. **重入**：所有外部入口 `nonReentrant`；ETH 转账（`_safeSendEth`）在所有状态更新之后；`grep` 全量确认无 `delegatecall`/`assembly`/`unchecked`/`selfdestruct`/`tx.origin`，唯一 `.call{value}` 在受保护的 ETH 出金。
6. **暂停语义**：`withdraw`/`repay`/`liquidate`/`handleBadDebt` **不受 pause 限制**（退出与清算通道永远可用），只有 `supply`/`supplyCollateral`/`borrow` 受 `whenNotPaused` —— 符合"熔断新增敞口但不锁死用户"的预期。
7. **利率模型分段**：`kink2 == kink1`（高波动/极端预设）时 `else if` 分支不可达，曲线退化为两段，与注释一致，无跳变。
8. **Round-trip 精度**：`_amountToWadUsd` / `_wadToAmount` 互为逆运算，双向 floor 的舍入方向在借入、取款、清算三处均**有利于协议**；6/8/18 位混算经 `wadScale` 归一，未发现可利用的累计误差。
9. **无密钥泄露**：前端/服务端 `grep` 无 `dangerouslySetInnerHTML`、无 `eval`、无 `process.env.*KEY`（除 `NEXT_PUBLIC_WC_PROJECT_ID`，公开无妨）；`.env` 未被 git 跟踪。
