## 1. 结论

**现在不要广播。** 但不是因为合约本身不行——**合约是我这一轮最放心的部分**。是因为有一个 30 分钟能改完的配置错误，会让协议上线后**大约 92% 的时间处于不可用状态**，而它恰好被你们所有的测试都漏过去了。

修完这份清单里的 6 项（估计 1–2 天），我认为可以上，并且建议**用小额度软启动**而不是一次性放开。

## 2. 决定性证据：H2 不是推测，是你们自己测出来的

完整证据链，全部出自本仓库文件：

| # | 出处 | 内容 |
|---|---|---|
| 1 | `contracts/src/oracle/ChainlinkOracle.sol:36` | `uint256 public maxStaleness = 3600;` → **运行时只接受 1 小时内的价格** |
| 2 | `docs/Fork主网dress rehearsal报告.md:62` | "**稳定币 feed 更新间隔可远超文档 heartbeat（实测 11–13h）**" |
| 3 | 同上 | 应对方式是"已将 `DeployMainnet` **预检**新鲜度放宽到 26h"——**只改了部署前的检查，没改运行时的 3600** |
| 4 | `docs/冷启动与运营方案.md:99` | "稳定币 feed 更新慢（10h+）属正常……勿误报" |
| 5 | `scripts/feed-health-check/feeds.ts:15-19` | 5 个 feed 的 `heartbeatSec` 全登记为 `86400` |
| 6 | `contracts/script/DeployMainnet.s.sol` | **全文没有一处调用 `oracle.setMaxStaleness(...)`** |

**代入你们实测的数字算一下**：稳定币 feed 每 11–13 小时更新一次，而协议只接受 1 小时内的价格 → 新鲜窗口占比 ≈ 1/12 ≈ 8% → **协议只有约 8% 的时间是可用的，92% 的时间是坏的**。

一旦某个稳定币 feed 超过 1 小时没更新：

```
ChainlinkOracle._readPrice  → require(block.timestamp - updatedAt <= 3600) ❌ revert
        ↓
LendingPool._priceOf        → 同样 revert
        ↓
_debtValueWad / _collateralValueWad 全线 revert
        ↓
USDC 市场：borrow ❌  部分 repay ❌  withdrawCollateral ❌  liquidate ❌  handleBadDebt ❌
```

**最要命的是清算通道也一起死。** 坏账不会被处理，只会静默累积——而这正好发生在你想清算的时候（价格波动之后市场安静下来）。

### 为什么 229 个测试 + 5000 fuzz + 4 个不变式 + Slither 0 findings + fork 8/8 全绿，却抓不到？

这是我认为比这个 bug 本身更值得你记住的三点：

1. **可设价模式把真源整个绕过去了。** Sepolia 的全部 E2E 都跑在 `SwitchableOracle.useSettablePrice = true` 下，`getAssetPrice` 直接返回管理员设的价，**根本不经过 Chainlink 的 staleness 检查**。也就是说 `ChainlinkOracle` 在"新敞口"路径上的行为，**从未在任何一次部署里被执行过**。而主网部署明确"不部署 SwitchableOracle"（`DeployMainnet.s.sol:19`）——**测试环境和生产环境走的根本是两条代码路径**。

2. **fork rehearsal 用的是自定义 `ForkOracle`。** `ForkMainnet.t.sol` 的 `ForkOracle` 注释写着"默认 `latestRoundData()` 直读真实 Chainlink proxy"——它**绕过 `ChainlinkOracle` 合约本身**。所以 8/8 全绿，但 `maxStaleness` 一次都没被行使过。

3. **测试断言的是"实现"，不是"需求"。** `Oracle.t.sol:61` 断言 `"stale price"` 会 revert——它**忠实地把 3600 这个错误默认值编码成了正确行为**。没有任何一条测试问过："一个 11 小时前的稳定币价，对协议来说能不能用？" 测试越多，这类"断言了错误规格"的用例越会给人虚假的安全感。

> 顺带说一句：README 里"passed Base mainnet fork dress rehearsal"这个表述，鉴于 fork rehearsal 用的是自定义 oracle wrapper，**建议改成更准确的措辞**，否则对外披露时会误导评审者（也误导你自己）。

## 3. 上线前必须完成的 6 项（Go/No-Go 门禁）

按"不做就不能广播"的标准筛的，全部有明确改法（详见修改方案）。

| # | 项目 | 位置 | 为什么是门禁 | 工作量 |
|---|---|---|---|---|
| **1** | **`DeployMainnet` 必须显式调用 `setMaxStaleness`（≥ 26h）+ `setMaxDeviation`（10~15%）** | `contracts/script/DeployMainnet.s.sol` | 不修，上线即 92% 时间不可用 | 15 分钟 |
| **2** | **部署脚本新增"逐资产 feed 可读 + description 匹配 + 档位非零"部署后自检（`require` 而非打印）** | 同上 | 漏配 feed / 喂错 feed 会静默上线 | 1 小时 |
| **3** | **`MainnetDeployAndTransfer` 加 `require(safe != deployer)` + "撤销前确认接收方已拿到权限"门禁** | `script/MainnetDeployAndTransfer.s.sol` | 一次笔误 → 协议永久失去管理能力，**不可逆** | 1 小时 |
| **4** | **前端价格源改读 `deployments.oracle`，删掉硬编码 $2506 兜底，改为 fail-closed** | `frontend/src/lib/` | 不修，用户看到的 HF/LTV 全是错的 | 3~4 小时 |
| **5** | **两个部署脚本在 Base fork 上**不带 `--broadcast`**完整干跑一遍** | — | 部署脚本本身从没被端到端执行过（fork rehearsal 用的是 `new` 直接部署，**没走 `DeployMainnet.s.sol`**） | 2 小时 |
| **6** | **设置供应/抵押上限（`MAINNET_*_CAP`）** | 部署时的 env | **你们建好了上限机制，但默认值是 0 = 不限制** | 30 分钟 |

**关于第 5 项我特别想强调**：fork dress rehearsal 是"在 fork 上 `new` 出全套合约",**并没有跑 `DeployMainnet.s.sol`**。也就是说那条 400 行、包含角色授予与撤销顺序的部署脚本，**至今没有被真正执行过一次**。而它是不可逆的。这是我建议里投入产出比最高的一项。

**关于第 6 项**：`_setSupplyCap` 的实现是 `if (cap > 0) pool.setMarketSupplyCap(...)`，`MAINNET_*_CAP` 默认 `uint256(0)`。所以按默认配置部署出来的池子是**无上限**的——而你们自己的冷启动文档第 2 节写着"单资产供应上限 $5 万 / 总 TVL ≤ $20 万"。机制建好了，但没接线。

## 4. 上线策略建议：不要 big bang

我的核心建议不是"多测"（你们测了很多了），而是**把"一次性放开"改成"用上限把最大损失锁死"**。

理由很直接：**你们无法通过测试消除"未知的未知"。** 上面那个 bug 证明了这一点——它不在任何测试的覆盖范围里。既然测试的边际收益已经很低，那就换一种风险控制手段：**让任何一个未知 bug 的损失上限是你承受得起的**。

具体建议：

| 阶段 | 额度 | 观察目标 | 放行条件 |
|---|---|---|---|
| **软启动（第 1–2 周）** | 单市场 supply cap **$5 万**，抵押 cap 与之匹配；TVL 上限 **$10–20 万** | 坏账 = 0；至少经历 **2 个完整的"价格波动→清算"周期**；跨过至少 **3 个"稳定币 feed 长时间不更新"的窗口** | 全部指标达标 |
| **第 3–4 周** | 单资产提至 $10 万 | 清算执行成功率、储备覆盖率、利用率稳定性 | 治理（Timelock）放行 |
| **第 2 个月起** | 单资产 $20–25 万 | 真实借款需求与利率分布 | 逐步 |

同时：
- **不要在上线时做激励活动。** 期权/积分/空投只会把 TVL 快速拉高，而你的上限还没验证过——激励带来的量正好会撞上未验证的额度。等软启动跑通再说。
- **把"未审计"写在明面上**（README 已经写了，很好），并且**不要把它删掉**。
- **per-user 借款上限**：你们文档第 2 节自己也点出"合约暂无 per-user cap"。软启动期的实际风险主要来自**单个大额仓位**（$5 万 TVL 里一个 $4.9 万仓位 = 集中风险）。合约层加 per-user cap 属于批次 C；在它落地前，**只能在运营层控制（邀请制、人工过一遍大额仓位）**，这一点必须有人真的盯着，写进流程而不是写进文档。

## 5. 上线后前 72 小时的操作要点

1. **立刻链上验证 6 件事**（不要只看脚本日志）：
   ```bash
   cast call $POOL "treasuryAddress()(address)"
   cast call $ORACLE "maxStaleness()(uint256)"      # 必须是 26h 级别，不是 3600
   cast call $ORACLE "maxDeviation()(uint256)"      # 建议 1e17，不是 3e17
   cast call $ORACLE "lastValidPrice(address)(uint256)" $ETH   # 必须 > 0
   cast call $POOL "marketSupplyCap(uint8)(uint256)" 0         # 必须是设定值，不是 0
   cast call $POOL "hasRole(bytes32,address)(bool)" $DEFAULT_ADMIN $SAFE  # 必须 true
   ```
2. **把"紧急刹车"到底是哪个函数搞清楚并写进值班手册。**
   这一点容易被误解：**`LendingPool.pause()` 不是全停**——它只挡 `supply`/`supplyCollateral`/`borrow`，清算、还款、提现照常。
   **真正的核按钮是 `ChainlinkOracle.pause()`**：它让所有读价 revert，从而把 `borrow`、`withdrawCollateral`、`liquidate`、`handleBadDebt`、部分 `repay` 一起停掉（`supply` 的 `withdraw` 和全额 `repay` 仍可用——这是好事，用户退出通道不该被锁）。
   请把这两个开关的**区别和各自影响面**写进值班手册，并确保 PAUSER 密钥在值班人手上。
3. **专门盯"安静时段"。** H2 的触发条件就是市场安静 —— 具体来说：**周末、凌晨 4 点、以及任何一次大波动之后的 12 小时**。在这些时段主动调一次 `getAssetPrice(USDC/USDT/DAI)`，确认不 revert。这比跑一百个测试更能验证修复。
4. **配置 keeper 周期调用 `oracle.updatePrice(asset)`**，否则偏差保护会随 `lastValidPrice` 变旧而钝化（见修改方案 B5/M3）。
5. **监控至少先做到"不要什么都不盯"**：现在 `services/monitor/config/positions.json` 的 `users` 是**空数组**，即监控当前盯的是零个仓位。软启动期仓位少，人工能覆盖——但**必须有人负责每天过一遍全量仓位**，直到事件集/Subgraph 补上。

## 6. 不建议现在做的事

- ❌ **不要再加测试来"确保安全"。** 你们已经有 229 个测试、5000 fuzz、4 个不变式、Slither 0 findings。上面那个 bug 说明**问题不在测试数量，而在测试与真实环境的差距**。边际收益极低。真正该补的是**"用真实 oracle + 真实 feed + 真实陈旧数据跑一遍"**这一类测试（修改方案里已列）。
- ❌ **不要为了抢上线而把批次 C（合约改动）塞进这次发布。** 合约改动需要整组重部署 + 测试重跑 + 尺寸收敛（LendingPool 只剩 3,090B 余量）。H2 用**链上 `setMaxStaleness` 调参**就能缓解，**不需要动合约**。先把软启动跑起来，把 C 批当作第二次迭代。
- ❌ **不要在没有外部审计的情况下放开额度。** 如果预算有限，至少**定向找一次"预言机 + 清算 + 部署流程"的专项评审**（1–2 天量级，比全量审计便宜一个数量级），并且**用第 4 节的上限把损失锁在你承受得起的范围内**。这两件事有任一件没做，就不该放开额度。

## 7. 一句话总结

**合约很扎实，问题在"合约之外"。你的测试一直在验证"代码是否按写的运行"，但从没验证过"写的东西是否符合真实世界的 feed 行为"——fork 报告里那句"实测 11–13h"已经告诉了你答案，只是它被写进了文档，没被写进代码。**

修掉那 6 项，用上限软启动，你就具备了上线的条件。现在广播的话，第一天就会接到"借款按钮点了没反应"的反馈——而那时你会以为是自己前端的问题。
